# Milestone 2 — Weeks 3 & 4: Data Collection & AI Model Development

> PRD scope: Collect and preprocess transportation datasets · Develop crowd density
> prediction models using ML algorithms · Build demand forecasting models for peak-hour
> analysis · Integrate AI models into backend services.

## 1. Data Collection & Preprocessing

Synthetic-but-realistic datasets generated by `backend/scripts/generate_data.py`
(deterministic seed 42), honoring the PRD's "no CCTV" constraint:

| File | Rows | Schema |
|---|---|---|
| `data/stations.csv` | 12 | id, code, name, line, zone, lat/lon, capacity_per_hour |
| `data/trains.csv` | 8 | id, code, model, capacity, status |
| `data/schedules.csv` | ~170 | train/station/direction, arrival/departure, headway_min, is_peak |
| `data/ridership.csv` | 14,400 | station × hour × 50 days: entries, exits, occupancy, congestion_level |
| `data/ticketing_events.csv` | 20,000 | event_id, station_code, timestamp, card_type, direction, gate_id, fare_amount |

Preprocessing (`app/ml/features.py`):

- Hour-of-day / day-of-week / is_weekend cyclical-ish encodings.
- Peak flag (7–10h, 17–20h) and lag features (previous-hour occupancy).
- Station one-hot + capacity normalization; train/test split by time order.
- Raw ticketing events land in MongoDB (`metroflow.sensor_events`) via
  `scripts/seed_db.py::seed_mongo_events()` — best-effort when Mongo is available.

## 2. Crowd Density Prediction Models

- Algorithm: **GradientBoostingRegressor** (scikit-learn) — chosen over heavier DL for
  tabular data, small footprint, and explainability.
- Target: occupancy per station-hour; features from `build_crowd_features`.
- Artifact: `models_store/crowd_model.joblib` (+ feature metadata).
- Metrics (held-out): **R² = 0.947, MAE = 0.0124** occupancy units.

## 3. Demand Forecasting Models

- Algorithm: GradientBoostingRegressor on entries target with same temporal features.
- Artifact: `models_store/demand_model.joblib`.
- Metrics (held-out): **R² = 0.9968, MAE = 1.30** passengers/hour.
- Peak-hour analysis surfaced via `/predictions/patterns` (AM/PM peaks, weekend factor,
  24h profile per station).

## 4. Backend Integration

- Loader with graceful fallback: `app/ml/model_wrappers.py` — if artifacts are missing,
  heuristic baselines keep endpoints alive (never 500s).
- Service layer: `app/services/prediction_service.py`
  - `predict_crowd(station_id, hours)` → hourly forecast + congestion classification.
  - `forecast_demand(station_id, hours)` → predicted entries/exits.
  - `smart_recommendations(db)` → per-station recommended headway from predicted load
    vs. scheduled capacity (clamped 2–15 min).
  - `traffic_patterns(db)` → historical pattern mining (Milestone-3 endpoint, built here).
- Endpoints wired in `app/api/v1/predictions.py` (JWT-protected).
- Frontend consumption: predictions page charts with confidence bands
  (`components/ForecastChart.jsx`), recommendations table, patterns table.
