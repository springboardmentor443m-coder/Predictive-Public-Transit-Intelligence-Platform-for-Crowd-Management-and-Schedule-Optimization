# MetroFlow

An AI-powered platform that predicts metro station crowd levels and
recommends scheduling adjustments, built as a working reference
implementation for the "Predictive Public Transit Intelligence Platform
for Crowd Management and Schedule Optimization" internship project.

## What this actually is

A decision-support tool, not a live camera/sensor system. It learns
patterns from historical-style ridership data (station, time of day, day
of week, holidays) and predicts how crowded a station will be, then turns
that prediction into a plain scheduling recommendation. No computer
vision or CCTV is used, matching the brief's explicit scope.

## How it maps to the official brief

| Brief module | This project |
|---|---|
| User Management | Simple login screen in the dashboard (demo credentials, not full JWT/role-based auth) |
| Crowd Monitoring | `train_model.py` prediction model + the map view in the dashboard |
| Scheduling Management | `scheduling.py` - threshold-based recommendation logic |
| AI Prediction | RandomForestRegressor predicting passenger count per station/hour |
| Alert & Notification | Dashboard banner when any station predicts "high" crowd |
| Analytics Dashboard | Summary stats + station table in the dashboard |
| Extra: NL query | `/query` endpoint - ask a plain-English question, get a data-backed answer |

**Simplified on purpose, per mentor guidance:** no Docker, no cloud
deployment (AWS/Azure), no React/Next.js frontend, no
PostgreSQL/MongoDB/Redis, no TensorFlow, no Socket.IO, no full
auth/role system. Everything runs locally in plain Python. See the
project's mentor notes for why - the evaluation focus is on application
logic and architecture, not infrastructure.

## Data

**Real data** from the MTA Subway Hourly Ridership 2022-2024 dataset
(Kaggle: yaminh/mta-subway-hourly-ridership-2022-to-2024). The original
file is ~51 million rows across hundreds of stations and two payment
methods; it was processed down to a workable, well-scoped dataset:

1. Combined the omny/metrocard payment-method split into one ridership
   total per station/timestamp (`groupby` + `sum`).
2. Filtered to the 12 busiest stations by total ridership (Times Sq-42
   St, Grand Central-42 St, Union Sq, Herald Sq, Penn Station, and
   others) - a reasonable scope for a 4-week build, and mirrors how a
   real transit authority would prioritize its busiest hubs.
3. Engineered `hour`, `day_of_week`, `is_weekend`, and `is_holiday`
   (US 2023 federal holidays) features from the raw timestamp.

Final dataset: `data/metroflow_final.csv`, 300,242 rows, zero nulls,
covering all 12 stations across a full year with realistic ridership
values (1 to ~21,000 passengers per station-hour).

To extend this: swap in more stations, a different city's data, or a
wider date range - just keep the same column names
(`station, borough, lat, lon, hour, day_of_week, is_weekend, is_holiday,
passenger_count`) and `train_model_real.py` will work without changes.

## How to run it

Requires Python 3.9+. From the project root:

```bash
pip install -r requirements.txt

# 1. Dataset is already included: data/metroflow_final.csv
#    (see "Data" section above for how it was sourced and cleaned)

# 2. Train the model
cd model && python train_model_real.py && cd ..

# 3. Start the backend (leave this running in its own terminal)
cd backend && uvicorn main:app --reload --port 8000

# 4. In a NEW terminal, start the dashboard
cd dashboard && streamlit run app.py
```

Open the Streamlit URL it prints (usually `http://localhost:8501`).
Log in with `operator` / `metroflow123` (demo credentials - change these
before sharing the app with anyone else).

## Results

The trained model achieves an 82% improvement in mean absolute error
over a naive baseline (always predicting the average), with an R² of
0.95 on the synthetic dataset. On real-world data, expect these numbers
to be lower - synthetic data is generated from clean rules, so the model
has an easier time than it would with messier real-world patterns.

## Natural-language query feature

The `/query` endpoint currently uses simple pattern matching (regex) to
pull a station name and time out of your question, gets a real
prediction from the trained model, and phrases the answer in plain
English. The numbers always come from the model - this keeps the "smart
recommendations" feature honest rather than letting an LLM invent
figures.

**To upgrade this to a full LLM-powered version** (optional stretch,
once the core pipeline is solid): in `backend/main.py`'s `/query`
endpoint, after getting the prediction, send it as context to the
Claude or OpenAI API and ask it to phrase a more natural, conversational
answer - the LLM explains the number, it doesn't generate it.

## Limitations & what real deployment would add

- Uses synthetic data; a real deployment would need actual ticketing/GPS
  feeds and validation against real ridership patterns.
- Scheduling recommendations are threshold-based rules, not a full
  optimization solver (e.g. linear programming for vehicle allocation)
  - a reasonable scope choice for this timeline, documented as a known
  simplification.
- No real-time data pipeline; predictions are computed on-demand from
  historical patterns, not live sensor feeds.
- Login is a single hardcoded demo account, not a real user database
  with role-based permissions.
